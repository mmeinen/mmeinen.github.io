Create `js/scene/orbital.js` with the following exports. This module provides orbital mechanics formulas used by nav.js (Plan 02) and index.html (Plan 03). It does NOT import anything -- it receives BH_GM, planetData, and _planetGM as parameters or references globals (same pattern as combat.js).

**Orbit state constants:**
```javascript
const ORBIT_STATE = { ORBITING: 0, TRANSFER: 1, FREE: 2 };
```

**Body SOI radii table (nav-mode values, oR already doubled):**
Use the Hill sphere formula with gameplay floor: `max(d * cbrt(planetGM / (3 * BH_GM)), planetRadius * 2.5 + 1.0)`.

Pre-computed lookup (computed once at load, referencing planetData and _planetGM):
```
BODY_SOI[-1] = 8.0   // Black hole (hardcoded, no Hill sphere)
BODY_SOI[0]  = ~7.0   // Jupiter
BODY_SOI[1]  = ~6.5   // Saturn
...etc per RESEARCH.md table
```

Store as a function `computeSOI(planetIndex)` that returns the gameplay SOI, plus a `BODY_SOI` array initialized at module load for quick lookup. BH index is -1.

**Default orbit altitudes table:**
```
DEFAULT_ORBIT_ALT[-1] = 5.0  // BH
DEFAULT_ORBIT_ALT[0]  = 4.0  // Jupiter
...etc per RESEARCH.md table
```

**Helper functions:**
- `getBodyGM(index)` -- returns BH_GM for index -1, _planetGM[index] otherwise
- `getBodyRadius(index)` -- returns ~2.0 for BH (event horizon), planetData[index].radius otherwise
- `circularVelocity(GM, r)` -- returns `Math.sqrt(GM / r)`
- `computeHohmannDV(r1, r2, GM)` -- returns `{ dv, transferTime }` using vis-viva equation per RESEARCH.md Pattern 1
- `circularizeOrbit(flyPos, flyVel, bodyPos, bodyGM)` -- sets flyVel to circular orbit velocity tangent to radius vector (per RESEARCH.md Pattern 3). Modifies flyVel in-place.

**Lagrange point computation:**
- `computeLagrangePoints(planetIndex, time)` -- returns `{ L1, L2, L4, L5, r_hill }` per RESEARCH.md Pattern 4
- Only compute for planets with index 0, 1, 3 (Jupiter, Saturn, Neptune -- the 3 largest). Return null for other indices.
- Each L-point is `[x, 0, z]` in world coordinates, co-rotating with the planet.

**Key implementation notes:**
- The module needs access to `BH_GM`, `_planetGM`, `planetData`, and `planetPosAtTime`. Since these are globals defined in nav.js (loaded before orbital.js), reference them directly (same pattern as combat.js referencing globals).
- All Y coordinates are 0 (ecliptic plane lock).
- Nav-mode orbit radii are doubled (oR * 2). The SOI table must use nav-mode radii. Since `enterNavMode()` doubles oR in place, orbital.js should compute SOI lazily or accept that oR values change.
- Approach: provide an `initOrbitalData()` function called from `enterNavMode()` after oR doubling, which fills BODY_SOI and DEFAULT_ORBIT_ALT arrays using current planetData values.

**Capital ship geometry (append to math.js):**

Create `createCapitalShipGeometry()` following the exact same pattern as `createGruntGeometry()` -- using tri()/quad() helpers with auto-computed face normals, returning `{ positions, normals, indices }`.

Design spec (per RESEARCH.md):
- Bounding box: ~1.2 x 0.3 x 0.8 (wider and longer than Grunt's ~0.4 x 0.4 x 1.0)
- Smooth wedge nose (NOT diamond cross-section like Grunt)
- Bridge/command tower on top (NOT a dorsal fin like Grunt)
- Wide-set engine nacelles (wider spacing than Grunt's narrow nacelles)
- Forward-swept wing plates flanking the hull
- ~120-180 triangles total (Grunt has 62)
- Key visual distinction: smoother, sleeker silhouette vs Grunt's angular diamond shape

Vertex layout approach:
1. Main hull: tapered wedge from rounded nose to wide stern. Use 6-8 longitudinal stations with varying width/height to create a smooth profile.
2. Bridge tower: small raised section on top, centered ~30% from nose. Rectangular with beveled edges.
3. Nacelles: two engine pods at rear, offset laterally ~0.35 from centerline (wider than Grunt's 0.1). Each nacelle is a small box with rear face vertices tagged for engine glow.
4. Wing plates: two angled panels extending forward from nacelle mounts, swept ~20 degrees forward. Triangular or trapezoidal.

Engine glow vertex identification: nacelle rear face vertices should have z < -0.35 (matching shader threshold). The shader will add emission based on vertex z position.

**Ship shader update (modify shaders.js):**

Update `shipVS` to pass vertex position (object space) to fragment shader via a new varying `v_objPos`:
```glsl
varying vec3 v_objPos;
// In main(): v_objPos = a_shipPos;
```

Update `shipFS` to add engine glow:
- Add `uniform float u_thrustIntensity;` (0.0 = no thrust, 1.0 = full thrust)
- After computing base lighting, add engine glow for vertices where `v_objPos.z < -0.35` (near nacelle rears):
  ```glsl
  float engineMask = smoothstep(-0.30, -0.40, v_objPos.z);
  vec3 engineColor = vec3(0.3, 0.5, 1.0) * u_thrustIntensity * engineMask;
  // Add to final color (additive)
  ```
- Keep existing diffuse + ambient lighting intact. Engine glow is purely additive.
- Do NOT change enemyVS/enemyFS -- only ship shaders.
